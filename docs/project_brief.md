# Project Brief: Audio-First Touch-Typing Tutor

## 1. Project overview

Develop a cross-platform, audio-first application for teaching ten-finger touch typing to blind and visually impaired learners, primarily adults undergoing digital rehabilitation at **VÁI (Vakok Állami Intézete), Budapest**.

The application should be implemented in **Flutter**, targeting:

- Web browsers
- Windows desktop
- Linux desktop

The initial language is **Hungarian**, including Hungarian keyboard layouts and accented characters.

The application must work independently of screen readers such as NVDA and JAWS. It should handle all instructional speech, feedback, navigation, and interaction through its own audio system.

It should nevertheless coexist gracefully with screen readers when they are enabled.

## 2. Educational approach

The goal is not merely to improve typing speed, but to teach people with little or no usable vision to operate a standard physical keyboard accurately and confidently.

The curriculum will ideally be obtained from experienced VÁI instructors. **Do not invent a full curriculum yet.**

The system should accommodate:

- Beginners with no keyboard experience
- Learners who previously typed visually
- Different learning speeds and individual needs
- Progressive exercises, from finger positioning to fluent text entry

Lessons should be defined as content, separately from application logic, allowing educators to edit, replace, and extend the curriculum without modifying source code.

## 3. Core functionality

### Audio-first interface

All essential interactions must work without looking at the screen.

- Spoken instructions and navigation
- Audio identification of keys and expected actions
- Immediate feedback on correct and incorrect keystrokes
- Ability to repeat instructions
- Adjustable feedback verbosity and pacing
- Clear transitions between lessons and exercises
- Fully keyboard-controlled menus and settings

Distinguish between prerecorded Hungarian speech, synthesized speech, and nonverbal sound effects.

Audio coordination is important: instructions, typing feedback, and sound effects must not overlap unintentionally.

### Typing lessons

- Progressive introduction of keys and finger movements
- Character, sequence, word, sentence, and extended-text exercises
- Hungarian keyboard layout support
- Accuracy measurement
- Speed measurement when pedagogically appropriate
- Individual progress tracking
- Repetition of difficult material
- Configurable completion criteria

The architecture should support different exercise types without hardcoding individual lessons.

### Gamification

Gamification should motivate without distracting from learning.

Possible features:

- Achievements and milestones
- Progression through levels
- Personal challenges
- Improvement records
- Optional auditory rewards

All gamification must be usable without vision and adjustable or removable for learners who find it distracting.

### Instructor support

Provide a visual interface useful for instructors and partially sighted learners.

Eventually, instructors should be able to review individual progress, identify difficulties, and select suitable exercises.

Avoid unnecessary complexity in the initial implementation.

## 4. Technical considerations

### Architecture

Separate at least the following concerns:

- Curriculum and lesson definitions
- Exercise execution and keyboard input
- Audio management
- Learner progress and assessment
- User interface and navigation
- Gamification

Prefer a maintainable architecture without excessive abstraction.

### Audio

Investigate suitable Flutter packages and approaches for cross-platform audio playback and Hungarian speech synthesis.

Evaluate prerecorded versus generated speech, particularly regarding:

- Hungarian pronunciation quality
- Latency and responsiveness
- Offline operation
- Consistency across web, Windows, and Linux
- Deployment size and complexity

Ideally, the application should operate offline after installation, wherever the platform permits.

### Keyboard handling

Pay particular attention to physical key positions versus characters generated by the active keyboard layout.

Hungarian accented characters, Shift combinations, Backspace, and other special keys require deliberate handling.

The implementation must behave consistently across target platforms.

### Accessibility

The application must be independently usable by a completely blind person, including its initial setup, menus, error recovery, and progress reporting.

Screen readers are not part of the core architecture, but compatibility with them should be preserved where possible.

### Data

Plan for local progress persistence initially. Avoid requiring user accounts, servers, or cloud services for basic functionality.

## 5. Existing reference

An existing open-source Java application may provide useful ideas:

https://github.com/eknagy/tugip

TUGIP (TízUjjas GépÍró Program) contains an extensive Hungarian touch-typing curriculum and prerecorded instructions.

It works on Linux but has an outdated graphical interface.

Treat TUGIP as a reference for understanding possible functionality and lesson structures, not as a required dependency or an authoritative curriculum. Check licensing before reusing any code or resources.

## 6. Proposed development stages

**Stage 1 — Architecture and feasibility**

- Examine relevant Flutter capabilities and packages.
- Investigate audio playback and Hungarian speech options.
- Investigate cross-platform keyboard handling.
- Propose a curriculum data format.
- Identify major technical and accessibility risks.

**Stage 2 — Minimal functional prototype**

Implement a small, complete learning experience:

- Application startup with audio guidance
- Keyboard-only navigation
- Two or three sample exercises
- Spoken instructions and keystroke feedback
- Exercise evaluation
- Basic saved progress

Test the prototype without using a screen or screen reader.

**Stage 3 — Educational validation**

Collaborate with VÁI instructors and blind learners.

Evaluate usability, instructional effectiveness, appropriate feedback, and exercise progression.

Integrate the actual VÁI curriculum.

**Stage 4 — Full application**

Develop the complete curriculum engine, instructor features, progress tracking, gamification, and cross-platform distribution.

## 7. Instructions for Codex

**Do not start implementation yet.**

First, review the concept critically and propose:

1. A suitable Flutter architecture.
2. Audio and keyboard-handling technologies.
3. A flexible representation of lessons and exercises.
4. The smallest meaningful prototype.
5. Important risks, unresolved questions, and architectural decisions.

Keep the initial design simple. Avoid prematurely adding databases, accounts, cloud infrastructure, or complex gamification.

Do not assume that educational requirements are finalized. They will be developed collaboratively with VÁI instructors.

The immediate goal is a technically sound plan and a narrowly scoped prototype specification, not a completed application.
